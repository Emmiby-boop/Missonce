### 2.1 P0 级问题 — 必须立即处理

#### 问题 1：preview.js 与 wallpaper-preview.js 代码重复

**位置**：
- `WeChat Mini/subpackages/preview/preview.js`（1104 行）
- `WeChat Mini/subpackages/wallpaper-preview/wallpaper-preview.js`（1311 行）

**现状**：两个文件合计 2415 行，约 60%+ 代码逐行重复，包括：
- `downloadImage` / `doDownload` / `saveToAlbum` — 下载流程完全重复
- `buildSimilarList` / `ensureResourceId` — 数据构建逻辑重复
- `safeDecodeURIComponent` / `_prepareShareImageUrl` — 工具方法重复
- 连调试 `console.warn('[DL] ...')` 日志都完全一致（各 10 处）

**影响**：
- Bug 修复需同步两处，遗漏概率极高
- 功能迭代成本翻倍
- 已有 `behaviors/` 机制但未充分利用

**修复方案**：
```
第一步：将以下方法下沉到 behaviors/preview-common.js
  - downloadImage / doDownload / saveToAlbum
  - buildSimilarList / ensureResourceId
  - _prepareShareImageUrl / safeDecodeURIComponent
  - 临时文件清理逻辑（fs.unlinkSync）

第二步：preview.js 和 wallpaper-preview.js 只保留差异逻辑
  - preview.js: 头像特有逻辑（相册保存方向、尺寸适配）
  - wallpaper-preview.js: 壁纸特有逻辑（壁纸尺寸、设置壁纸入口）

预期效果：两文件各缩减至 300-400 行
```

#### 问题 7：Service 层形同虚设

**现状**：`cloudBaseService.ts` 定义了完整的 CRUD 基类和 9 个预定义实例，但多数页面直接调用 `db.collection()` 绕过 Service 层。

**修复方案**：
```typescript
// 错误做法（当前）
const res = await db.collection('resources').doc(id).update({ data: { ... } })

// 正确做法
// 1. 在 service 中封装业务方法
class ResourceService extends CloudBaseService {
  async updateTags(id: string, tags: string[]) {
    return this.update(id, { tags })
  }
  async batchAddTag(ids: string[], tag: string) {
    return this.batchUpdate(ids, { tags: db.command.push([tag]) })
  }
}

// 2. 页面中调用
await resourceService.updateTags(id, tags)
```

import { defineStore } from 'pinia'
import { ref, computed } from 'vue'

export const useAuthStore = defineStore('auth', () => {
  const admin = ref<AdminProfile | null>(null)
  const isAuthenticated = computed(() => !!admin.value)

  async function login(account: string, password: string) {
    const res = await callCloudFunction('adminAuth', { action: 'login', account, password })
    admin.value = res.admin
    // Pinia 持久化插件自动处理 localStorage
  }

  function logout() {
    admin.value = null
  }

  return { admin, isAuthenticated, login, logout }
})

## 六、团队技术能力提升路径

### 6.1 代码规范建设

#### 6.1.1 建立代码审查 Checklist

每次提交 PR 前自查：

```
□ 无 console.log 残留（使用 logger 或构建移除）
□ 无空 catch 块（至少 console.error）
□ 函数不超过 50 行（超过则考虑拆分）
□ 文件不超过 500 行（超过则考虑拆分）
□ 无硬编码值（常量提取到 config/）
□ 无 as any / @ts-ignore（必须有类型声明）
□ 无原生 alert/confirm/prompt（使用 UI 组件）
□ 错误处理有用户反馈（ElMessage / wx.showToast）
□ 命名一致（camelCase 函数/变量，PascalCase 组件/类）
□ 无重复代码（如发现重复，提取到公共模块）
```

#### 6.1.2 建立 ESLint 自定义规则
