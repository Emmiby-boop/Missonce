### 🟡 P1-2：4 处云函数空 catch（虽不是 0 但需确认语义）

**实测**：
```
$ grep -rnE "catch\s*\(.*?\)\s*\{[^}]{0,3}\}" --include="*.js" cloudfunctions/
（已 0 处）
```
✅ 方案 v1.0 报告的云函数 12 处空 catch 已清零。

**保留 2 处的语义复核**（`components/waterfall/waterfall.js:74, 131`）：
- L74: `try { ... } catch (e) {}` — 瀑布流列数初始化失败
- L131: `try { ... } catch (e) {}` — 滚动事件异常吞噬

这两处都属"非关键失败，回退到默认值"语义，**保留空 catch 是合理的**，但建议加注释说明：
```js
} catch (e) {
  // 列数计算失败：静默回退到默认 2 列
}
```

### 🟡 P1-3：132 处 console.log — 100% 收敛到非生产环境

**实测**：

### 🟡 P1-4：`storageManager.js` 仍使用 3 处 `getSystemInfoSync`

**位置**：`utils/storageManager.js:111, 136, 158`

**问题**：方案中已建议替换为异步 `wx.getWindowInfo()`/`wx.getAppBaseInfo()`，但实测这三处还在用同步 API。同步 API 会阻塞 JS 线程，**在启动期调用会直接拖慢首屏**。

**修复**：
```js
// 现状（L111）
const sysInfo = wx.getSystemInfoSync()

// 建议
const sysInfo = wx.getWindowInfo()  // 异步可用，无需 await
```

实测 `storageManager.js` 顶部已经有 `_windowInfo` 全局缓存，所以只需把首次获取从 sync 改成 async 即可。

### 🟡 P1-5：云函数 auth.js 中 6 处 `db.collection` 直调

**实测**：
```
pages/index/index.js:200:    wx.cloud.database().collection('resources').doc(id).get()
pages/index/modules/home-cache.js:12-13
pages/profile/profile.js:217-218, 387, 416-417, 463
```

**问题**：方案 P1 中已建议"页面只与 Service 层交互，不直接接触 db"，但 4 个文件里依然在直调 `wx.cloud.database().collection(...)`。

**为什么这是问题**：
- 业务规则散落（profile.js 同一个数据库有 5 处直调）
- 错误处理无法统一
- 单元测试 mock 困难

**建议**：将 `home-cache.js` 和 `profile.js` 里的直调都迁到 `utils/api/*.js` 对应的 service 方法里。

### 💭 P2-2：`console.group` 配对不正确

**位置**：`utils/performance.js:30-35`
```js
console.group(`[Performance] ✅ ${pageName} 页面加载完成`)
if (Object.keys(extraInfo).length > 0) {
  // 这里是空的！应该 console.table(extraInfo) 或 console.log(extraInfo)
}
console.groupEnd()
```

**问题**：`if` 块内是空代码，开发者明显是"准备打印 extraInfo 但没写完"。**死代码，应删除**或补全。

### 💭 P2-3：`preview-common.js` 使用 `setInterval` 30 分钟清理

**位置**：`behaviors/preview-common.js:22-29`
```js
setInterval(() => {
  // 清理 _tempUrlCache
}, 5 * 60 * 1000)
```

**问题**：
- Behavior 中的 `setInterval` 不会在页面卸载时自动清理（Component 的 lifecycle 不覆盖 Behavior）
- 用户反复进入预览页 → 多个 setInterval 累积
- **内存泄漏 + 多余唤醒**

**建议**：用 `Page.onUnload` 清理，或改用 `wx.nextTick`/`requestIdleCallback` 模式。

### 💭 P2-4：`ad-unit.js` 759 行 — 广告组件过度复杂

**位置**：`WeChat Mini/components/ad-unit/ad-unit.js`

**问题**：单组件承担 4 种广告类型（native/interstitial/rewarded/banner）+ 9 个外部 props + 多重定时器管理。**单元测试与维护成本都高**。

**建议**：拆为 `ad-native` / `ad-interstitial` / `ad-rewarded` 三个组件，由 `ad-unit` 做容器与配置管理。

## 六、性能瓶颈清单

### 瓶颈 1：启动期同步 API 阻塞首屏（已修复 × 3 / 待修 × 3）

**已修复**：
- ✅ `wx.getStorageSync` 全部移除（仅剩 `removeStorageSync` 5 处，语义合理）
- ✅ `wx.getAccountInfoSync` 改为懒加载（`utils/logger.js`）
- ✅ `ad_daily_count` 预热（`utils/storageManager.js:48`）

**待修**：
- ❌ `utils/storageManager.js:111,136,158` 仍有 `getSystemInfoSync` 三处

### 瓶颈 2：GIF 不暂停（基线已识别，未实施）

方案中已建议"可视区外暂停 GIF 节省 30-50% 流量"，**目前未实施**。`behaviors/preview-common.js` 中只缓存了 `cloud://` 临时URL，未做 GIF 暂停。

**建议**：
- 微信原生 `image` 组件支持 `show-menu-by-longpress` 但**不支持 GIF 暂停**
- 需要用 Canvas 绘制 GIF（用 `wx.createOffscreenCanvas`）才能精准控制
- 或者：图片 `lazy-load` + 离屏时将 `src` 替换为静态首帧

### 瓶颈 3：瀑布流虚拟滚动已实现但被禁用

**位置**：`components/waterfall/waterfall.js:81-95`

代码注释明确说明：
> 瀑布流项高度不一致（壁纸9:16/头像1:1/文案矮卡/广告高卡），单一估算高度必然不准... 因此首页已禁用虚拟滚动

**现状**：
- 实现了 850+ 行业务级虚拟滚动代码
- 但 `enableVirtualScroll` 默认 `false`，首页禁用
- 仅在 `preview.js` / `wallpaper-preview.js` 启用但**仍可能跳变**

**建议**：
- 删除未启用的虚拟滚动代码（约 100 行） — **死代码**
- 保留文档化注释说明"暂未启用原因"
- 等找到"预计算项高度"方案后再启用

### 瓶颈 4：`preview-common.js` setInterval 内存泄漏

见 💭 P2-3。
